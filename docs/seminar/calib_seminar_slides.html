なぜ ChArUco Board なのか？
5 / 36

チェッカーボード (Chessboard)

  • 長所: サブピクセル精度が極めて高い
  • 短所: オクルージョン（隠蔽）に極端に弱い
  • 一部が見切れると全交点のインデックス照合に失敗し、1点も検出できない

ArUco マーカー

  • 長所: 各マーカーに固有 ID があり、一部が隠れても個別検出可能
  • 短所: マーカー四隅の位置精度が低く、高精度な較正には不向き

ChArUco Board (ハイブリッド)

  • 両者の利点を統合！
  • マーカーから各チェッカー交点の絶対 ID を特定
  • 画面端で見切れても検出可能
  • 交点自体は高精度なチェッカー交点

画面周辺部の歪み補正に不可欠

広角レンズ・魚眼レンズでは画面の四隅で歪みが最大になります。ChArUco なら、ボードを画面の角に半分はみ出させても有効な標本点を取得できます。

チェッカーボードの最大の泣き所は見切れに弱い点でした。ChArUco はこれを完全に克服しています。

手動較正の課題: 「ブレ」と「重複」
6 / 36

課題 1: モーションブラー (ブレ)

  • 作業者が片手でボードを持ち、もう片手でキーボードやマウスを押すと手振れが発生
  • ブレた画像ではコーナー検出座標が数ピクセル狂い、再投影誤差が悪化

課題 2: 構図・姿勢の偏り (重複)

  • 同じような距離・傾きで何枚も撮影しても、較正行列のランクは上がらない
  • 画面中央ばかりの標本を集めると、周辺部で歪み補正が破綻（過学習）

自動取得が満たすべき2つのゴール

  1. モーション検出: ボードがピタリと静止している瞬間（ブレなし）だけを自動検出する
  2. 幾何多様性判定: 直前に記録した標本と「位置」「距離」「傾き」が十分に異なる場合のみ記録する
この2つの条件を自動で判定できれば、作業者はカメラの前でボードを色々な向き・位置に動かして止めるだけで、完璧な標本セットが集まります。

void Calibration::updateMotion(float deltaTime,
  float motionThresholdPx, float minStableTime, int minCorners)
{
  // 共通コーナーの変位量を合算
  float totalDist = 0.0f; int commonCount = 0;
  for (size_t i = 0; i < charucoIds.size(); ++i) {
    for (size_t j = 0; j < prevCharucoIds.size(); ++j) {
      if (prevCharucoIds[j] == charucoIds[i]) {
        totalDist += cv::norm(charucoCorners[i] - prevCharucoCorners[j]);
        ++commonCount;
        break;
      }
    }
  }
  if (commonCount >= 4) currentMotion = totalDist / commonCount;
  else currentMotion = 999.0f;

  // 閾値(2.0px)以下ならタイマー積算、超えたらリセット
  if (currentMotion <= motionThresholdPx) stableDuration += deltaTime;
  else stableDuration = 0.0f;

  isCurrentlyStable = (stableDuration >= minStableTime);
}

なぜ外接矩形 (Bounding Box) ではダメなのか？

画面端で見切れた場合、外接矩形の中心やアスペクト比は欠落したコーナーの影響を極端に受けます。また、斜め傾きを矩形で表現することは困難です。

1. 重心位置 (Centroid)

$$\bar{x} = \frac{m_{10}}{m_{00}}, \quad \bar{y} = \frac{m_{01}}{m_{00}}$$

ボードが画面のどこにあるかを表す（平行移動指標）。

2. 慣性半径 (Spread)

$$R = \sqrt{\mu_{20} + \mu_{02}}$$

重心からの点群の幾何学的広がり。カメラとの距離（スケール）を表す。

3. 主軸角度 (Orientation)

$$\theta = \frac{1}{2} \operatorname{atan2}(2\mu_{11}, \mu_{20} - \mu_{02})$$

点群の慣性主軸の傾き（$-90^\circ \sim +90^\circ$）。ボードの回転を表す。

画像モーメントを使うことで、点群の一部が欠けていても統計的にロバストな姿勢パラメータを取り出せます。

Calibration::BoardPoseFeatures Calibration::computeFeatures(const std::vector<cv::Point2f>& corners)
{
  BoardPoseFeatures features;
  if (corners.size() >= 4) {
    cv::Moments m = cv::moments(corners);
    if (m.m00 > 0.0) {
      // 1. 重心位置 (画像平面上の配置)
      features.centroid = cv::Point2f(m.m10 / m.m00, m.m01 / m.m00);

      const double mu20 = m.mu20 / m.m00;
      const double mu02 = m.mu02 / m.m00;
      const double mu11 = m.mu11 / m.m00;

      // 2. 慣性半径 (スケール・距離)
      features.spread = static_cast<float>(std::sqrt(std::max(0.0, mu20 + mu02)));

      // 3. 主軸角度 (ボードの傾き -90°〜+90°)
      features.angleDeg = static_cast<float>(0.5 * std::atan2(2.0 * mu11, mu20 - mu02) * 180.0 / CV_PI);
    }
  }
  return features;
}
OpenCV の cv::moments() は輪郭だけでなく点群の vector に対しても呼び出すことができます。

bool Calibration::isDiverseEnough(...) const
{
  if (!hasRecordedShot || allCorners.empty()) return true;
  const auto cur = computeFeatures(charucoCorners);

  // 1. 重心移動量 (対角長に対して ≧ 5%)
  float diag = std::hypot(size.width, size.height);
  float dist = cv::norm(cur.centroid - lastRecordedFeatures.centroid);
  if (diag > 0.0f && (dist / diag) >= minDistanceRatio) return true;

  // 2. スケール変化 (直前比 ≧ 12%)
  if (lastRecordedFeatures.spread > 0.0f) {
    float scaleDiff = std::abs(cur.spread - lastRecordedFeatures.spread)
                      / lastRecordedFeatures.spread;
    if (scaleDiff >= minScaleRatio) return true;
  }

  // 3. 主軸角度変化 (周期性を考慮して ≧ 8°)
  float angleDiff = std::abs(cur.angleDeg - lastRecordedFeatures.angleDeg);
  while (angleDiff > 90.0f) angleDiff = std::abs(180.0f - angleDiff);
  if (angleDiff >= minAngleDeg) return true;

  return false;
}

いずれか 1 つのクリアで十分

  • OR 条件で判定している点がポイント。
  • 「位置はそのままで傾きだけ変えた」場合も合格。
  • 「角度はそのままでカメラにグッと近づけた」場合も合格。
  • 「少し横にずらした」場合も合格。
  • まったく同じ場所で静止し続けた場合だけがブロックされる。

OpenCV VideoCapture の限界

  • 内部バッファの不可視性: 2〜3フレーム内部に溜まるため、カメラの動きに対して表示が常に 50〜100ms 遅れる。
  • MJPG / H.264 デコードの重さ: CPU で愚直にソフトウェアデコードするため、4K や 60fps で CPU 使用率が高騰。
  • 遅延初期化ができない: デバイス列挙時にすべてのモードを開いて調査しようとしてフリーズする。

Media Foundation 直接制御のメリット

  • 超低遅延: CODECAPI_AVLowLatencyMode で内部キューイングを完全無効化。
  • ハードウェアデコード: GPU / DXVA 支援の MFT デコーダを自動探索して活用。
  • 遅延初期化 (Lazy Init): メタデータ列挙時はデコーダを作らず、キャプチャ開始時に構築。

アーキテクチャ上の目的: カメラ基底クラスのデカップリング

Camera.h 基底クラスから OpenCV 依存（cv::Mat 等）を完全に排除し、生のバイト配列（std::vector<GLubyte>）に統一。画像処理部とキャプチャ部の結合度を最小化。

教材としても、Windows の本格的なマルチメディア API の扱い方を学べる貴重なサンプルになっています。

デコーダ内部のフレームバッファリング（Bフレーム待機等）を禁止。

なぜこれが効くのか？

通常、H.264 や MJPG デコーダはスループット向上のため内部に 3〜5 フレームを蓄積してから出力します。低遅延モードを有効にすることで、「1フレーム入力されたら即座に1フレーム出力する」同期動作になり、遅延が最小化されます。

この CODECAPI 設定を行うか行わないかで、Webカメラ映像の「手元との追従性」が劇的に変わります。

商用レベル MFT プログラミング最大の難所

MJPG/H.264 デコーダは、最初のフレームヘッダーを読み込んだ瞬間、ProcessOutput が MF_E_TRANSFORM_STREAM_CHANGE エラーを返して停止します。これに対応しないと映像が一切流れません。

`CamMf` での実装ステップ (`CamMf.cpp` L818-L980)

  1. pDecoder->GetOutputAvailableType を走査し、再ネゴシエーション用の NV12 サブタイプを特定。
  2. 現在の入力タイプから解像度、フレームレート、アスペクト比を出力タイプへコピー。
  3. pDecoder->SetOutputType(0, pNewOutputType, 0) で新しい出力型を確定。
  4. 出力バッファの再アロケーション: createDecoderBuffer() を呼び、64バイトアラインされたメモリバッファを再作成。
  5. 後段のカラーコンバータを再セットアップし、今回の ProcessOutput を再試行。
多くの簡易サンプルではこのエラー処理が省略されており、実機カメラを繋いだ瞬間にクラッシュしたり動かなかったりします。

HRESULT CamMf::createDecoderBuffer() {
  MFT_OUTPUT_STREAM_INFO streamInfo{ 0 };
  pDecoder->GetOutputStreamInfo(0, &streamInfo);

  // NV12 の 16 ピクセルアラインメント計算
  const auto alignedWidth  = static_cast<UINT32>((width + 15) & ~15);
  const auto alignedHeight = static_cast<UINT32>((height + 15) & ~15);
  const auto cbDecoderCalc = static_cast<UINT32>((alignedWidth * alignedHeight * 3) / 2);

  const auto cbDecoder = (streamInfo.cbSize > cbDecoderCalc) ? streamInfo.cbSize : cbDecoderCalc;
  const auto alignment = (streamInfo.cbAlignment > 0) ? (streamInfo.cbAlignment - 1) : 63;

  SafeRelease(&pDecoderBuffer);
  // AVX/SSE 命令に最適化されたアラインメント付きバッファを作成
  return MFCreateAlignedMemoryBuffer(cbDecoder, alignment, &pDecoderBuffer);
}

なぜアラインメントが重要なのか？

ハードウェアデコーダや MFT カラーコンバータは内部で SIMD（AVX2 / SSE4）命令を多用します。メモリが 64 バイト境界に整列されていない場合、非整列メモリアクセス例外や大幅な性能低下を招きます。

MFCreateAlignedMemoryBuffer を使うことで、OS が自動的に SIMD に最適なアラインメントを保証してくれます。

2つの動作モード

  • 低遅延最優先 (`prioritizeLatency == true`):
    • メインスレッドの処理速度に関わらず、キャプチャスレッドは最高速でループ。
    • 古いフレームは上書き破棄し、常に最新の映像を維持。
  • 全フレーム処理 (`prioritizeLatency == false`):
    • メインスレッドが前フレームを消費するまで std::this_thread::yield() で待機。
    • コマ落ちのない正確なフレームシーケンスを保証。
用途に応じてこの2つのモードを実行時に切り替えられるのが calib の大きな強みです。

// 1. アロケータを作成しストリームにバッファを割り当て
allocator = std::make_unique<libcamera::FrameBufferAllocator>(camera);
allocator->allocate(stream);

// 2. 各バッファプレーンをプロセスのアドレス空間に mmap
for (const auto& buffer : allocator->buffers(stream)) {
  std::vector<MappedPlane> planes;
  for (const auto& plane : buffer->planes()) {
    void* memory = ::mmap(NULL, plane.length, PROT_READ, MAP_SHARED,
                          plane.fd.get(), plane.offset);
    planes.push_back({ memory, plane.length });
  }
  mappedBuffers[buffer.get()] = std::move(planes);

  // 3. リクエストを作成しバッファをバインド
  auto request = camera->createRequest();
  request->addBuffer(stream, buffer.get());
  requests.push_back(std::move(request));
}

ハードウェア DMA 直結の威力

ファイルディスクリプタ plane.fd は Linux カーネルの DMA-BUF です。ISP ハードウェアが物理メモリへ直接フレームを書き込み、ユーザー空間はそれを mmap で直接読み取ります。

メモリの二重コピーを防ぎ、カーネル空間からユーザー空間へのコピーコストを完全になくす手法です。

void CamLibcam::requestComplete(libcamera::Request* request)
{
  if (request->status() == libcamera::Request::RequestCancelled) return;

  // 完了バッファを取り出し
  auto bufferMap = request->buffers();
  libcamera::FrameBuffer* buffer = bufferMap[stream];
  const auto& planes = mappedBuffers[buffer];

  const uint8_t* src = static_cast<const uint8_t*>(planes[0].address);
  {
    std::lock_guard<std::mutex> lock(mtx);
    // フォーマット別展開 (XBGR8888, RGB888, YUYV, R8...)
    copyOrConvertFrame(image.data(), src);
    captured = true;
  }

  // ★ リクエストを再利用してカメラキューへ再投入！
  if (running) {
    request->reuse(libcamera::Request::ReuseBuffers);
    camera->queueRequest(request);
  }
}

リングバッファの循環メカニズム

  • 通常 3〜4 個のリクエストがキューイングされている。
  • ハードウェアが 1 個完了 $\to$ コールバック発火。
  • データをコピーしたら、直ちに request->reuse() で初期化。
  • camera->queueRequest(request) で再びハードウェアのキューへ返却。
  • メモリ確保・解放ゼロ の永久循環ループ！

ARM CPU での配慮

浮動小数点の乗算を排除し、すべて 32-bit 整数乗算と 8 ビット右シフト（>> 8）に変換。コンパイラによる自動 NEON ベクトル化が働きやすい構造にしています。

Q1. 自動取得が全然反応しない

  • コーナー数不足: ボードが近すぎてコーナーが 6 点未満になっていませんか？（最低 6 点必要）
  • 手振れ: 平均変位が 2.0px を超えていませんか？一度机に置くか両手でしっかりホールドしてください。
  • 構図の重複: 直前の標本から大きく動かしましたか？（対角 5%、スケール 12%、角度 8°）

Q2. 再投影誤差が小さくならない

  • 画角の隅に標本がない: 中央ばかりでなく、四隅に見切れさせて配置してください。
  • 距離の変化がない: 至近距離（画面いっぱいの大）と中遠距離（小）を取り混ぜてください。
  • 傾きのバリエーション: 正面だけでなく、上下左右に 30度程度傾けたショットを入れてください。
